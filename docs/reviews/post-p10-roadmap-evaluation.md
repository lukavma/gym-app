### B's identity boundary: users are not Entra tenants

Multiple application users means multiple internal `users.id` accounts and isolated data, even with one Entra directory. A single-tenant Entra app registration can admit directory members and guests; multitenant registration permits identities from other directories and broadens policy/consent testing. For a small pilot, one workforce tenant with explicitly admitted members/guests is the default candidate, subject to the invitees' actual identity needs. It does not require organization workspaces, cross-user sharing, coach roles or an app `tenant_id` on every training table. [Microsoft: single- and multitenant apps](https://learn.microsoft.com/en-us/entra/identity-platform/single-and-multi-tenant-apps).

Easy Auth handles platform authentication before requests reach the app; on Linux it passes identity through headers. Application authorization remains necessary. The existing middleware and `requireUserId()` read iron-session, so turning on Easy Auth alone would leave two incompatible authentication gates rather than provision application accounts. Plan an explicit adapter/cutover and preserve JSON/API unauthorized behavior. [Microsoft: App Service authentication](https://learn.microsoft.com/en-us/azure/app-service/overview-authentication-authorization).

Admission must be explicit: a tenant-valid token is not an invitation. Choose a small application allowlist or suitable enterprise-app assignment policy, and verify it with the intended users. Easy Auth also documents principal and tenant restrictions; principal IDs and application/client IDs are different controls. No broad Graph permissions, group-sync subsystem or automatic public signup is justified. [Microsoft: Entra provider configuration](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-provider-aad).

B2's stable key is a proposed application design supported by Microsoft's identity semantics: email/display names are mutable; `oid` identifies the directory object and `tid` supplies its tenant context. Guest objects can differ across tenants. Preserve internal account identity rather than rekeying every training row. [Microsoft: ID token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference).

Trust `X-MS-CLIENT-PRINCIPAL` only behind the authenticated App Service path. Microsoft documents that App Service injects these headers and prevents external callers from setting them through that path; a local server accepting arbitrary headers does not inherit that guarantee. Handle mapped claim names, reject missing/unexpected principals and keep test identity injection confined to local/CI operation. [Microsoft: user identity headers](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-user-identities).

The account-bound outbox is essential even where existing foreign-entity checks work: [bodyweight/recovery sync](../../src/server/sync/service.ts) writes a date-grain entry under the **current authenticated user**, so replaying an ownerless old operation after switching accounts can create data in the wrong account without ever referencing a foreign workout ID. Client binding should select a queue only after online identity confirmation and prevent wrong-account sends; the server must continue deriving authorization from the authenticated identity, never trust a client-selected `userId` as authority.

Define **auth expiry** separately from **explicit logout/account switch**. Expiry should retain the current account's queued work for same-account recovery. Explicit logout must stop flushing and remove access to private local views; handle pending work with clear sync/retain-locked/discard choices according to the accepted policy. Never silently erase queued training or promise remote revocation can delete data on a disconnected device. A conservative pilot may postpone account switching until pending work is resolved, while still preventing cached-data disclosure after logout.

Easy Auth's `/.auth/logout` clears its session cookies/token store and performs provider sign-out for Entra; that does not implement this app's IndexedDB/cache lifecycle. Its return URL must be allowed, and the app must avoid immediately navigating back into automatic sign-in. Test account selection and re-login on the installed PWA. [Microsoft: customize sign-in/out](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-customize-sign-in-out).

Recommended B dependency order: B1 → B2/B3/B4 → B5/B6 → B7 acceptance and a controlled pilot. Reassess D-03 within B1/B5 because its explicit expansion trigger fires; several isolated users do not by themselves require new merge algorithms, but the acceptance cannot simply be inherited from the one-account MVP. No tenant-management platform or general RBAC system is proposed.

## 6. Scaling: likely limits and useful measurements

**No supported user count can be derived from this repository.** The performance evidence is a local single-account workload, not a concurrency/capacity test. Registered accounts, simultaneously active accounts, history size, reconnect batches and per-request query cost are distinct dimensions.

ADR-009 documents Linux App Service B1/Node 24/Always On and PostgreSQL 16 Flexible Server B1ms, 32 GiB, West Europe, seven-day PITR, public networking with firewall rules and no HA/replicas. Provisioning is documented manually, not represented as desired-state IaC. The R3 predeployment report previously verified a live server's version/region and performed a name check; it is not evidence of current SKU, instance count, memory/CPU limits, connection ceiling, backup retention, alerting or firewall posture. Historical euro estimates in ADRs are not a verified current bill.

The current [deploy workflow](../../.github/workflows/deploy.yml) uses OIDC, serializes production deploys, runs CI quality gates, opens a temporary runner-IP DB rule, migrates/seeds, closes the rule and deploys the standalone app. README's older sequence and firewall shorthand should not override that code. Seed-before-app remains a compatibility constraint. [CI](../../.github/workflows/ci.yml) already runs deterministic offline/PWA E2E with disposable PostgreSQL; the full browser suite remains outside that job.

Useful existing baseline: the [dashboard remediation verification](metrics-dashboard-remediation-verification.md) records **780 sessions, 6,240 session exercises, 31,200 set logs, local p95 53.48 ms**. The [R1 verification](athletic-measurement-profiles-release-1-remediation-verification.md) explains the corrected comparison and a 42.03 ms R1 p95. These are fixture-specific reports, not end-user HTTP latency, current-tree benchmarks or proof that Azure meets the same numbers. Do not reuse the dashboard implementation's earlier undersized-fixture ~21 ms result as the representative baseline.

Current Microsoft guidance describes Burstable PostgreSQL as credit-based and not recommended for production workloads; depleted credits can cause serious degradation. That is a reason to revisit the documented personal-app tradeoff before B and observe credit headroom, not proof that this deployed app is currently overloaded. Microsoft exposes CPU-credit and other DB metrics. [Compute guidance](https://learn.microsoft.com/en-us/azure/postgresql/compute-storage/concepts-compute), [monitoring metrics](https://learn.microsoft.com/en-us/azure/postgresql/monitor/concepts-monitoring).

Do not assume B1 automatically scales with traffic: Microsoft's comparison places manual scaling at Basic and above, metric/schedule autoscale at Standard and above, and automatic traffic scaling on supported Premium tiers. Treat scale-out as a measured capacity/configuration decision with a database connection budget. [App Service scaling comparison](https://learn.microsoft.com/en-us/azure/app-service/manage-automatic-scaling).

A useful future measurement package is **S**: reproduce the documented local fixture; add a small two-account mixed workload with Today/metrics reads and reconnect writes; record query counts, HTTP p50/p95, error rate and drain time at stated concurrency. Then, only with separate authorization, compare actual app/DB resource metrics and device responsiveness. Define a pilot's acceptable delays and abort conditions from those results. This is sufficient before considering load infrastructure, caches, materialized aggregates, replicas or new hosting services.

For recovery planning, Azure PITR restores into a **new server**; a drill must cover validating that target and how the application would reconnect. A successful backup setting or job alone does not prove that process. [Microsoft: backup and restore](https://learn.microsoft.com/en-us/azure/postgresql/backup-restore/concepts-backup-restore).

Keep their paths stable; preserve original verdicts and add later forward-linked closure evidence instead of editing an old review to look green. The historical implementation plan should identify its delivered phase sequence and point to ROADMAP for **new priorities**, retaining any still-binding phase requirements until explicitly amended.

This resolves a tension in the workflow review: it recommends generated STATUS rows from report metadata, but also a hand-written first tranche. Start manually with one closeout editor. Reports own the factual verification results; STATUS is the authoritative current-state index of those facts and owner decisions. Do not have both metadata and STATUS independently decide what may run. If indexing later earns its cost, generate only evidence rows from the same reports; preserve a single human-selected current gate. No `report:index` implementation is needed now.

Apply only the durable parts of the [workflow evaluation](repository-agent-workflow-evaluation.md) and its [independent review](repository-agent-workflow-review.md):

1. **Small context packets and report deltas.** Name the task/review kind, base revision plus relevant dirty-file state, accepted scope, file ownership, input reports, exact next gate and authorization limits. New reports include a short header and cite earlier evidence; do not retrofit every legacy report. Use plain prompt/report templates if repeated copying is actually awkward.
2. **Preserve evidence levels.** Distinguish developer confidence, independent-review evidence and release evidence. Quote an executed command/result once with the relevant revision; cite it later while its inputs remain unchanged. Preserve mandatory migration/double-seed, sync/offline, concurrency negative-control and release/device checks. A diff-selected test subset is developer confidence, not permission to skip a required gate.
3. **One mutation owner per shared environment.** Readers may record a moving-tree limit; builds, generated files, database fixtures and negative controls need one owner. Cleanup only resources demonstrably created by that task; do not delete from a name prefix alone. Preserve uncommitted bytes when testing controls. Worktrees and port allocation are deferred until simultaneous writers demonstrably need them.
4. **Correct current instructions before scripting them.** CI's actual order is migrations → global seed → build/start/health → smoke account setup → per-account seed → E2E fixture → offline suite. Keep that sequence intact. The workflow review's old missing-`rg` observation no longer applies here (`rg` worked); `sync/service.ts` is currently `i/lf w/lf`, and later implementation reports record format success. No `.gitattributes` exists, so an LF policy is still a reasonable small follow-up, but do not call formatting currently broken or normalize another task's dirty files from the historical report alone.

Do **not** build the proposed launcher, orchestration state machine, worktree manager, generalized cleanup registry, six skills or large script suite. Do not adopt the old “half the wall-clock” or token-percentage promises: the review correctly challenged their evidence. No new skill is necessary for this tranche; first correct any stale command in the existing one. Do not carry cosmetic concurrency-environment-variable renaming as future work.

After one real delivery chain using these conventions, record builds invoked, full versus targeted E2E runs, report size, bootstrap failures and leftover resources. Only then consider one tested helper for the dominant repeated problem. Any verification helper must print executed steps and exit codes, fail on failures, and never make a skipped gate look green. This is a stop-and-measure rule, not the first milestone of an orchestration project.

## 8. Recommended sequence and owner decisions

Recommended sequence:

1. Finish the existing Catalog Expansion 1 review/closeout and its separately authorized controlled release; preserve the owner-reported completion of Athletic Profiles R1–R3.
2. Make one small STATUS/ROADMAP/BACKLOG and workflow-convention pass. Deliver PI-007 Recovery as the sole optional product slice before pausing.

4. Select **one** demonstrated daily-use improvement next, or continue using the app. Start the pilot branch only after explicitly choosing its identity/isolation/ops scope.

Material owner decisions, at most three:

3. **Next engineering commitment:** prioritize **account export and demonstrated recovery (recommended)**, keeping weekly dump automation and the remaining Phase 10 header/performance work explicitly deferred until separately scoped; or consciously defer durability too.

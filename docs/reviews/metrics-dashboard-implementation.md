## 3. Judgment calls

1. **Editor's read statement count.** §11.5 suggests `GET /api/metrics/selection` runs "two statements." Correctly computing each selected row's `state` (`estimate` / `no_current_estimate` / `not_available` / `turned_off`) needs a fact query the two-statement sketch doesn't have room for — without it the editor could not show *why* a row has no current estimate, which is the field's stated purpose. Implemented as up to four statements (timezone read, selection join, candidates query, an all-time bounded-by-≤5-ids fact query). No acceptance criterion pins the editor's read-path statement count (only the *write* path is explicitly exempted in §11.3); correctness and cross-screen consistency were prioritized over the informal note.
2. **The editor's fact query is not 90-day-windowed.** Unlike the dashboard's own step 9, `queryAllTimeFactRows` (in `selectionService.ts`) has no time bound — it mirrors the strength detail endpoint's own all-time scan, batched across ≤5 ids in one round trip. Justification: the X-12/§11.2 "avoid a per-exercise all-time scan" concern is specifically about the *dashboard's* per-load-time cost; the editor is opened only when the athlete manages the list, not on every dashboard read, so the frequency profile that motivated the window bound doesn't apply the same way. The value returned (state only) is unaffected by the choice, since `deriveStrengthReport` computes its own internal 90-day filter regardless of how much history it's handed.
3. **`confidence` / `latestPoolAgeDays` nulled outside `state: "estimate"`.** The DTO type declares both nullable but §11.2's "project only X, Y, Z" wording doesn't explicitly gate them on `state`. Chosen to null them when there is no current estimate to attach them to, matching how `currentE1rmKg`'s own nullability is explicitly gated. This changes nothing observable in practice for `latestPoolAgeDays` (already null in every non-estimate case, since the pool that produces it is empty exactly when `currentE1rmKg` is null) and only suppresses an otherwise-meaningless `confidence` value (e.g. `"low"` when the pool is empty) for the two ineligible states.
4. **Bodyweight 30-day change is computed from raw (unrounded) 7-day means, rounded once.** §4's notation section states the DTO carries unrounded numbers "except where a rule says otherwise" — M-7's own field is the stated exception (rounded to 0.1 kg), but M-8's *difference* is a separate quantity; computing it from the two raw means and rounding once avoids a double-rounding discrepancy against literally subtracting the two already-rounded M-7-style values.
5. **Step 3 (training set rows) always issues its query, even with zero session ids.** Verified empirically that `drizzle-orm`'s `inArray(column, [])` compiles to a literal `false` predicate, not an invalid empty `IN ()` — so the statement runs unconditionally, matching the spec's literal "steps 1, 2, 3, 8, 10, 11 always run; only step 9 is conditional" contract, rather than adding an extra conditional that would silently diverge from the documented statement-count table on a fresh, training-history-free account (an edge case A-12's own fixtures don't specifically exercise, but which the general contract statement covers).
6. **A-6(c) (duplicate-exercise-at-two-positions fact-order sensitivity) is not independently re-derived for metrics.** The metrics estimate index reuses `deriveStrengthReport` unchanged and only supplies the SQL `ORDER BY exercise_id, started_at, position, set_number` the binding contract requires; the underlying order-sensitivity behavior this proves is already fixture-proven by the strength module's own (untouched) test suite. Re-deriving it here would test the strength module a second time under a different name rather than testing anything metrics-specific.
7. **A-19(i) (cold-navigation offline) has no metrics-specific new test.** `/metrics` and `/metrics/exercises` are simply absent from `OfflineShell`'s allowlist (`src/ui/OfflineShell.tsx`, untouched), so a cold offline navigation to either route takes the exact same generic `OfflineRouteNotice` code path every other non-Today route (e.g. `/exercises`, `/programs`) already takes and which that component's own existing behavior already covers structurally. No new code was written for this case, so there was nothing metrics-specific to prove.

## 5. Negative-control evidence

Three focused mutations were made to already-passing production code, run against the specific test each was meant to protect, confirmed failing, then reverted byte-for-byte (confirmed by re-running the full suite green afterward; none of the three files carries a tracked baseline to `git diff` against since all three are new in this change, so restoration was confirmed by test re-run rather than `git diff`):

1. **`src/domain/metrics/training.ts`** — widened the future-guard comparison by ~11.5 days (`< guardMs` → `< guardMs + 999_999_999`). `metricsTraining.test.ts`'s mid-week guard case (a session on 2026-09-04, guard at 2026-09-03T00:00Z, both comfortably inside the training window) went from 0/0 to 1/1 sessions/work-sets — confirming the guard, not the window boundary, is what excludes it. (This negative control also caught a real weakness in the *original* test — its first future-session fixture sat exactly on the window's own exclusive boundary, so disabling the guard didn't change that particular assertion's result. The test was strengthened with the mid-week case before being used as the negative control.)
2. **`src/server/metrics/selectionService.ts`** — disabled the "already-selected" exemption (`if (false && alreadySelected.has(exerciseId)) continue;`). `metricsSelection.integration.test.ts`'s A-29 already-stored-exercise test failed immediately with `InvalidSelectionExerciseError`, reproducing exactly the bug this exemption was written to fix during development (see judgment call history — this was a real defect caught and corrected before this report, not a synthetic one).
3. **`src/server/metrics/service.ts`** — added one redundant, harmless extra `users` read at the top of `getMetricsDashboard`. All four of `metrics.integration.test.ts`'s A-12 exact-count assertions failed (11→12, 13→14, 10→11, 11→12), confirming the statement-count test is counting real statements, not a stale or approximate number.

All three files were restored to their pre-mutation text; `pnpm typecheck`, the full unit suite (836/836), and the affected integration files were re-run green after each revert and once more after all three.

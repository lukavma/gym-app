## 1. What was built, in one paragraph

Three new definition tables (`warmup_routines`, `warmup_routine_items`, `workout_template_warmup_routines`), a user-scoped domain/service/REST layer over them, a curated many-to-many association between workout templates and routines with a database-enforced at-most-one default, Today-bundle delivery of *only the resolved template's linked routines*, an inline dismissible warm-up card inside the existing workout screen whose checklist state lives exclusively in the device-local IndexedDB active-session aggregate, and routine-management UI reached from the Programs area. `workout_templates` gained no column. The sync contract, the progression engine, the volume engine, the outbox and every previously applied migration are byte-identical to `HEAD`.

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` PK | server-generated |
| `template_id` | `uuid` NOT NULL → `workout_templates.id` **ON DELETE CASCADE** | |
| `routine_id` | `uuid` NOT NULL → `warmup_routines.id` **ON DELETE CASCADE** | |
| `position` | `smallint` NOT NULL | 0-based link order |
| `is_default` | `boolean` NOT NULL DEFAULT `false` | |
| `created_at` / `updated_at` | `timestamptz` NOT NULL `now()` | |

- `uq_template_warmup_routine` — UNIQUE `(template_id, routine_id)`: a routine may be linked to a template at most once.
- `uq_template_warmup_routine_position` — UNIQUE `(template_id, position)`: deterministic ordering.
- `uq_template_warmup_routine_default` — **partial** UNIQUE index on `(template_id) WHERE is_default`: at most one default per template, enforced by PostgreSQL, not by service code.
- `ix_workout_template_warmup_routines_template_id`, `ix_workout_template_warmup_routines_routine_id`.

**`workout_templates` is unchanged.** There is no `warmup_routine_id` column anywhere, per the addendum.

The second half of the default invariant — *the default must be one of the template's linked routines* — is not expressible as a single constraint, so it is guaranteed structurally instead: `is_default` is an attribute **of a link row**, and the only write path replaces a template's entire link set in one transaction (§3.2). A default that is not linked therefore has no row to live on.

## 3. Lifecycle

### 3.1 Definition (planning world, online-only)

`create → replace (name + full ordered item list, one transaction) → hard delete`. Deleting a routine cascades to its items and to every template link; deleting a template (which itself cascades from its program) removes its links and leaves the routines alone. Nothing historical references a routine, so there is no archive state and no `SET NULL` anywhere.

### 3.2 Association (owner decisions O-1/O-2)

One endpoint, `PUT /api/templates/[id]/warmup-routines`, replaces the whole curated set atomically: submitted `routineIds` order becomes `position` 0..n-1, and `defaultRoutineId` marks exactly one of them (or none). Adding, removing, reordering, setting, changing and clearing the default are all this one call, so no two requests can interleave into a state where the default is not linked.

### 3.3 Execution (device-local, transient)

| Event | Behavior |
|---|---|
| **Start** | The existing single "Start workout" tap. `startSession` freezes the bundle's linked routines into `session.warmup` — `{ routines, selectedRoutineId: default ?? null, done: [false…], dismissed: false }` — or leaves it `null` when the template links none. `started_at` semantics unchanged (B-6). |
| **Select / switch** | `selectedRoutineId` set, `done` rebuilt from the newly selected routine's item count (progress resets deterministically). Local aggregate write, `ops: []`. |
| **Tick / untick** | `done[i]` flips. Local aggregate write, `ops: []`. |
| **Skip / undo** | `dismissed` toggles; `done` is preserved underneath, so undo restores the checklist exactly. Local aggregate write, `ops: []`. |
| **Reload / process kill / same-device resume** | The aggregate is the source of truth; the card, selection and ticks restore exactly, online or offline. |
| **Cross-device adopt** | `hydrateFromServer` writes the server DTO, which has no `warmup` → no card on the adopting device. Accepted v1 loss (O-3). |
| **Complete / discard** | `commitSessionMutation({ session: null, … })` deletes the aggregate. Warm-up state ceases to exist; nothing was ever written server-side (M-5, N-1). |
| **Definition edited/deleted mid-session** | Non-event: the session holds a frozen copy. |

Auto-collapse is presentation only and deliberately **not** persisted: the card renders collapsed when the checklist is complete or any non-warm-up set has been logged, and a header tap overrides that for the current render session. After a reload the rule is re-derived from the committed checklist, which is more predictable than restoring a stale manual toggle.

## 5. Deviations and judgment calls

1. **Route paths are top-level `/warmup-routines/*`, navigation is Programs-only.** O-4 says management belongs "under the Programs area, not a new top-level navigation destination". The *navigation* requirement is met exactly: the list renders beneath the program list on `/programs`, and no nav link was added (asserted in `warmupRoutines.spec.ts`). The *URLs* are top-level rather than `/programs/warmup/...` because `/programs/[id]` is a dynamic segment; a sibling static segment would work (Next.js prefers static) but is a fragile arrangement to inherit. Judgment call, flagged for review.
2. **`PUT`, not `PATCH`, for routines.** Routine + items are one consistency boundary (B-3); a partial patch would misdescribe the semantics. The whole routine is always replaced.
3. **Association list capped at 20 (`TEMPLATE_WARMUP_ROUTINES_MAX`).** Not specified by the evaluation; a sane bound against a pathological client, far above the 2–4 alternatives the product case describes.
4. **`linkedTemplateCount` on the routine record.** One grouped count query, so the delete confirmation can state what it will unwire (evaluation §9) instead of asking the user to guess.
5. **Warm-up mutators do not call `flushOutbox()`.** Every other mutator kicks a flush because it just enqueued something; these enqueue nothing. Skipping it makes "did a warm-up interaction touch the network?" answerable by inspection, and is asserted directly (§8.1).
6. **Auto-collapse state is not persisted** (rationale in §3.3).
7. **The checkbox is controlled by the committed aggregate, not optimistic.** Durability is the point of this design, so the checkbox reflects committed state; the consequence is a sub-frame revert between click and commit. This is why the E2E specs use `.click()` + a committed-counter assertion rather than Playwright's `.check()` — documented in `warmupWorkout.spec.ts`. Worth a reviewer's opinion; an optimistic layer would remove the flicker at the cost of a second source of truth.
8. **`aria-label="Linked warm-up routines"` added to the association editor's list.** Needed to distinguish "what is linked" from "what could be linked" (the picker below still lists every unlinked routine) — an accessibility improvement that also makes the assertion honest.
9. **`{ exact: true }` on `getByLabel("kg"/"reps")` in the new workout spec.** A warm-up item's accessible name is label + instruction, so the specified example item "Horizontal rotation — 10 controlled reps" makes the older specs' substring `getByLabel("reps")` ambiguous *when a warm-up card is on screen*. The new spec pins it exactly. **Pre-existing specs were not changed**; they never render a warm-up card, and the new specs delete their routines in teardown. A reviewer may reasonably want the older specs hardened too — deliberately left out of scope.
10. **`docs/architecture/data-model.md` was not updated.** That document is an up-front design artifact last touched at project foundation (§2.18/§2.19 for Phase 8's tables were written before Phase 8 shipped); Phases 5–8 added tables without amending it. The new schema files reference the evaluation document instead, matching the newer in-code convention (`phase-8-review.md B-3`, `Finding C`, …). Flagged as a conscious choice, not an oversight.
11. **Migration `0010` was applied to the local dev database `gymapp`.** Additive DDL only (three new tables), on the local Docker instance CLAUDE.md designates for local development and migration verification. Production was not touched.

Nothing in the specification was dropped or narrowed.

## 6. Error conventions

House conventions were followed exactly (`invalid_input` 400 with Zod issues, `not_found` 404, `name_conflict` 409, `unauthenticated` 401, 204 on delete). Two feature-specific 400s: `routine_not_found` (the association body names a routine that does not exist or is not the user's) and `default_not_linked`.

**Invalid UUID path parameters.** No route in this repository validated path parameters before this change; a malformed id reaches PostgreSQL's `uuid` type and raises SQLSTATE `22P02`, which no handler maps — an unhandled 500. Every new service entry point calls `isUuid()` (`@/domain/warmup/schema`) first and reports not-found instead, so the guard covers the Today-bundle path as well as the REST surface, not just the route handlers. Verified at both levels: integration (`treats a malformed uuid as not-found…`) and E2E (`a malformed routine id answers 404, never a 500`, covering `GET`/`PUT`/`DELETE` on routines and the template links route). Pre-existing routes were left alone — widening that fix is a separate change.

## 7. Legacy-cache tolerance (evaluation R-1 / Phase 5 L-4)

The server type declares `warmupRoutines` and `defaultWarmupRoutineId` as **required**; the client mirror in `src/sync/types.ts` declares them **optional**. That asymmetry is the mechanism, not an oversight: every client read site is forced by the compiler to handle absence, so a pre-upgrade bundle served from the service-worker `today-bundle` cache or the IndexedDB `bundleCache` after deploy renders no card instead of throwing. `StartSessionInput`'s two fields are optional for the same reason, and `freezeWarmupState` returns `null` for an empty routine list — so "no warm-up" and "pre-upgrade bundle" are the same representable state.

Exercised against **both** cache layers in `warmupWorkout.spec.ts` (§8.3, test 12): the SW's cached response body and the IndexedDB record are each rewritten with the warm-up keys deleted, the context goes offline, and Today loads and starts a normal workout with no card — while a follow-up API read confirms the server still has the routine linked as default, so the missing card can only have come from the doctored caches.

### 8.4 Hard boundaries

**No new sync entity or field on the wire.** `warmupWorkout.spec.ts` test 9 exercises every warm-up interaction (tick ×2, switch, tick, skip, undo), then asserts (a) every queued outbox op's `entity` is one of the seven existing `SYNC_ENTITIES`, and (b) the **actual `POST /api/sync` request bodies** contain none of: both routine names, both routine ids, three item labels, `"warmup"`, `"selectedRoutineId"`, `"dismissed"`, `"warmupRoutines"`. Positive controls in the same test confirm the scan is not vacuous (`"setLog"` and `"isWarmup":false` *are* present). `warmupActiveSession.test.ts` proves the same at the outbox level, with `isWarmup` explicitly excluded from the marker set — a naive `/warmup/i` scan would be wrong here, because `set_logs.is_warmup` is the unrelated pre-existing concept (I-8).

**Static boundary — `warmupBoundary.test.ts`**, built on the same AST import-graph walker as `progressionBoundary.test.ts`:

- Progression and volume (both domains, plus `server/progression`, `server/volume`, `server/sync`, and the sync/volume/history API routes) **never transitively reach any warm-up module**. `app/api/today-bundle/route.ts` and `app/api/active-session/route.ts` are deliberately *not* roots for this claim and the reason is documented in the file: they legitimately reach the warm-up service, because the bundle carries the linked routine *definitions* (O-2).
- No warm-up module (`domain/warmup`, `server/warmupRoutines`, `ui/warmup`, `app/api/warmup-routines`) reaches progression, volume, the sync contract, the outbox or the flusher. One documented carve-out — `domain/volume/schema.ts` reached *only* through `src/db/schema/*` table definitions that import its enum constants for CHECK constraints — is edge-specific and BFS-order-independent (`allParents`, the phase-8-review HIGH-2 hardening), and a dedicated test proves a direct warm-up edge into that same file still fails.
- `ui/workout/WarmupCard.tsx` is excluded from the second claim, with the reason stated: it imports the active-session store, which legitimately reaches progression. Its inability to write an execution fact is proven behaviourally instead.

### 8.5 Engine/metric equivalence

Each arm runs in its **own freshly migrated database**, because running both in one makes the second session's `historyDepthUsed` differ purely from the first session's existence — a failure with nothing to do with warm-ups. With that isolation, two sessions with byte-identical work sets — one on a template with a linked default warm-up routine, one on a template with none — produce:

- **identical progression output**: `action`, `target`, `strategyId`, `strategyVersion`, `classification`, `reasonCodes`, `confidence`, `inputs`, `computedBy`, `decisionStatus` all equal (and non-vacuous: the action really is `increase_load`);
- **identical volume output**: every week's `leaves`, `rollups`, `isDeload` and window dates equal (and non-vacuous: the warm-up arm really counted 3 chest work sets).

### 8.6 Database inspection

Two independent checks.

*(a) Integration, PGlite.* After a completed workout on a warm-up-linked template, every row of `workout_sessions`, `session_exercises`, `set_logs` and `recommendations` is cast to text and scanned: no routine name, no item label, no instruction, no routine id, no `warmup_routine`. Positive control in the same test: the dump *does* contain `Bench Press` and `completed`. Separately, `information_schema` confirms `set_logs.is_warmup` is the **only** warm-up-named column in the whole database, and the three new tables are the only warm-up-named tables. Casting *rows* rather than reading the catalog is what makes the unrelated `is_warmup` column unable to false-positive.

*(b) Real PostgreSQL 16, after the full E2E run.* Against `gymapp_warmup_e2e` (101 sessions, 101 session-exercises, 68 set logs, 4 recommendations, many of them produced by warm-up-using workouts):

```
execution_rows_mentioning_a_warmup_routine = 0
   (regex 'warm[- ]?up|Bike|Band external rotation|Wall slides|Horizontal rotation|5 min easy'
    over workout_sessions ∪ session_exercises ∪ set_logs ∪ recommendations row dumps)

information_schema warm-up columns:  set_logs.is_warmup   (the only one)
```

Positive control on the same 274 rows: 31 mention `completed`, 98 mention the template name — the scan reads real content. The three warm-up tables held **0 rows** at the end, which is itself evidence that hard delete and its cascades work: every spec deleted its routines in teardown, and the 101 sessions survived untouched.

## Appendix A — Correction, 2026-09-02 (review finding LOW-2)

*Appended after the independent review (`docs/reviews/warmup-routines-review.md`). Nothing above this line has been altered; §12's original text stands as written, and this appendix records what was wrong with it.*

### What §12 got wrong

§12 stated that `src/server/sync/service.ts` "is byte-identical to `HEAD` (verified: `git diff HEAD` empty, and the extracted `HEAD` blob hashes identically to the working copy), and running `prettier --check` on the extracted `HEAD` blob reproduces the same warning."

Two parts of that reproduction are **incorrect**:

1. The extracted `HEAD` blob does **not** hash identically to the working copy.
2. `prettier --check` on a correctly extracted `HEAD` blob does **not** reproduce the warning — it passes.

### What is actually true

The **conclusion** in §12 — the drift is real, pre-existing, and on a file this work must not touch — is correct. The mechanism is line endings, which §12 never identified:

```
worktree sha256                      fa2949707bc3d615b9a35ed78a22443416fed5e0b5c555a95ad79061bfb2b3a0
worktree sha256 after stripping CR   f9d9ebe64e94d6cf05dbd9d72d45a9324379133feef2e7eb0e8eaa5fae47f734  == the HEAD blob content
git blob object id                   d37a69b5c8fa9069af51cd0a25e583a9749ca927
git diff HEAD -- src/server/sync/service.ts    (empty)
worktree line endings                CR=1163  LF=1163  CRLF=1163   (every line ending is CRLF)
tracked .ts/.tsx files containing CR  1        (this file, and only this file)
core.autocrlf                        true
.gitattributes                       absent
```

So the file's **content** is identical to `HEAD`; only its line endings differ in the working tree, and `git diff` is empty because `core.autocrlf=true` normalises them on the way in. Prettier's sole objection is the CRLF endings — a CR-stripped copy of the worktree file, placed **inside the repository** so `.prettierrc.json` applies, passes cleanly:

```
probe sha256                       f9d9ebe64e94d6cf05dbd9d72d45a9324379133feef2e7eb0e8eaa5fae47f734
prettier --check <in-repo probe>   All matched files use Prettier code style!   (exit 0)
```

### Why the original check produced a misleading result

Two compounding mistakes, both worth recording so the same evidence is not produced again:

1. The blob was extracted with `git show HEAD:… | Set-Content -Encoding utf8NoBOM`. On Windows PowerShell, `Set-Content` writes CRLF line endings, so the "extracted blob" was re-encoded with exactly the line endings under test — it was never the blob's bytes. Use `[System.IO.File]::WriteAllText` (or `git cat-file blob`) to preserve them.
2. The extracted copy was written to a scratch directory **outside the repository**, where `prettier --find-config-path` reports `Can not find configure file` and prettier silently falls back to its own defaults instead of `.prettierrc.json`. A prettier check run outside the project is not evidence about the project in either direction.

### What did not change

The remediation deliberately did **not** fix the line endings: `src/server/sync/service.ts` is a review-gated file that must stay diff-clean, and normalising it would be a real modification to it. `pnpm format:check` therefore still reports exactly this one pre-existing failure, for exactly this reason. §12's summary table and its "deliberately not fixed" decision are unchanged and remain accurate.

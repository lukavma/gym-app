## 2. Final model (binding text in ADR-010 and the amended documents)

- `muscle_groups`: 18 rows = 17 leaves + the `back` rollup, distinguished by `kind ('muscle' | 'rollup')`. New leaves `lats`, `upper_back`, `adductors`. `lower_back` slug retained, displayed "Lower Back (Erectors)". Rollup membership `back → [lats, upper_back]` is a domain constant; no `parent_id`, DAG, or rollup table. Display sections are UI only.
- Contributions: leaf-only for new rows; a rollup slug passes an update only as carry-through of an existing row (the update path is delete-all-and-reinsert); legacy direct `back` rows are kept, counted, shown with an explicit reclassify affordance, never inferred.
- Aggregation: `Back = Lats + Upper Back + Unclassified Back` (last term hidden when zero); rollup raw sets deduplicated per set; nothing persisted; RP "Back" landmarks attach to the rollup only; `lats`, `upper_back`, `adductors`, `forearms`, `lower_back` have no RP landmarks and display without invented ranges.
- Sum-preservation invariant: after reconciliation, the rollup's weekly `effective` and `raw` equal the pre-v2 merged `back` series for every week; leaf history is deliberately re-interpreted under ADR-007. OD-03 (as-of history) remains parked.
- Rollback posture (corrected, see §10): **Release 1 is the point of no return for app rollback.** It already permits creating and reclassifying contributions onto `lats` / `upper_back`, which the pre-Release-1 build rejects on write and misrenders on read. Rolling back below Release 1 is safe only while no leaf contribution has been written; the Release 1 phone-acceptance step writes one and closes that window. After phone acceptance or any leaf write: roll forward by default, PITR only for catastrophe. A data reversal of the seeded remap, if ever needed, is the inverted state-predicated mechanism, never a SQL migration.

## 3. Reconciliation mechanism

Conditional idempotent updates in the seed pipeline (`seedMuscleGroups → reconcileContributions → seedExerciseCatalogForAllUsers`), keyed by the deterministic seeded id from the existing `seededExerciseId(userId, slug)` helper, restricted to `is_seeded = true AND muscle_group_id = 'back' AND NOT EXISTS target row`, touching only `muscle_group_id` (+ `updated_at`). No ledger (state-predicated idempotency is restore-safe; a ledger would be strictly worse), no pgcrypto, no name matching. Mandatory deployment-output reporting: `users, mapped, updated, noop, conflicts, customDirectBack`, with each conflict on its own `::warning::` line carrying user id, slug, exercise id and target; conflicts never silent, never deploy-failing (the state is honest and user-resolvable). Deployment scenarios (all-92, old-40, fresh, collided, renamed, hard-deleted, edited, removed, defensive conflict) are tabulated in ADR-010.

## 4. Compatibility proof and the two-stage rollout (the amendment)

Checked against the build that would be live during the seed step (`src/domain/exercises/schema.ts`, `src/app/api/exercises/**`, `src/server/exercises/service.ts`, `src/ui/exercises/*`, and a search for contribution readers elsewhere):

| Path                      | Finding                                                                                                                                                                                                                                                                                                                      |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API parsing               | Responses are not validated; reads pass unknown slugs through. `PATCH /api/exercises/:id` validates input with the 15-slug `muscleGroupSlugSchema` → saving any field of a reconciled exercise fails with 400 and the form shows a misleading "at least one primary is required" message. **Editor blocked — not cosmetic.** |
| Write-back race           | The editor's controlled `<select>` has no option for the unknown slug; the user can pick "Back" and save; `updateExercise` deletes all rows and reinserts `back` → a new direct `back` row, undoing the reconciliation until the next seed run. **Reachable with ordinary UI actions.**                                      |
| Rendering                 | Library renders the literal text `undefined` for reclassified primaries (cosmetic).                                                                                                                                                                                                                                          |
| Today / workout / history | No readers of `exercise_muscle_contributions` outside the exercises service — unaffected.                                                                                                                                                                                                                                    |
| `kind = 'rollup'`         | No runtime reader of `muscle_groups` in the old build (the seed runs from the new checkout) — invisible, safe.                                                                                                                                                                                                               |

Conclusion: a single deploy is not provably safe. ADR-010 and the implementation plan specify **two ordinary releases** with no added infrastructure:

- **Release 1 — capability:** `kind` migration; 18-row vocabulary; read compatibility; leaf-only creation validation with legacy carry-through; reclassify affordance; catalog unchanged; no reconciliation.
- **Release 2 — data:** catalog remap + `machine-hip-adduction`; reconciliation with reporting; seed runs under Release 1, which reads every slug and cannot write a new direct `back` row.

One deliberate placement within the amendment's allowed latitude ("define a simple rollout that guarantees compatible code is live before data semantics change"): **leaf-only creation enforcement ships in Release 1, not Release 2.** It is the precondition that makes Release 2's seed window provably safe; placing it in Release 2 would leave the write-back race open during that window. The accepted model and scope are unchanged, so no re-approval was sought. Residual (documented): a save of a legacy exercise that interleaves with the seconds of the seed step can carry its `back` row through; the next seed run reconciles it and the counts show it.

## 1. Verdict

**READY FOR REMEDIATION** — see the last line of this document. No user-data loss, no silent divergence, no incorrect recommendation, no authorization failure and no layout regression was found; every F1–F11 acceptance criterion that can be exercised off-device holds under independent fixtures. One MEDIUM defect stands in the exact F6 reconnect path the iPhone checklist exercises ("reconnect and verify convergence"): when the reply to an offline workout's first sync flush is lost after the server has applied it, the resend permanently dead-letters the session-create op (and any exercise whose skip/notes state changed in the same batch) even though the workout is fully and exactly-once persisted, and "Retry" can never succeed. ## 4. Findings

Severity legend: BLOCKER — data loss/silent divergence/authorization failure; HIGH — a binding acceptance criterion fails or a user-visible incorrect recommendation; MEDIUM — a binding contract breaks in a reachable path without data loss; LOW — hygiene, drift, latent or device-only UX.

### MEDIUM-1 — A lost reply to a multi-op reconnect flush permanently dead-letters already-applied ops (`invalid_lifecycle_transition` / `session_locked`)

**Contract:** `pwa-offline-strategy.md` §5 "ops are full-row upserts … replays converge. Retries are safe" and §6 (dead letters are for rejected ops). The Phase 8 B-2 remediation made the *single-op* lost-response retry idempotent (`src/server/sync/service.ts:213–246`, `tests/e2e/lost-response-retry.spec.ts`). It does not cover the shape the F6 flow actually produces: a batch that contains both the session-create and the completion (or a later state change of the same row).

**Mechanism:** on the replay, `applyWorkoutSessionUpsert` finds the row (`onConflictDoNothing` no-ops the insert), then runs the lifecycle check at `src/server/sync/service.ts:262–267` **before** the "exact-match replay of a terminal row is tolerated" check at `:270–277`: the replayed create carries `status: "in_progress"`, the row is now `completed`, `ALLOWED_SESSION_TRANSITIONS["completed"]` is empty → `invalid_lifecycle_transition`. Likewise `applySessionExerciseUpsert` (`:424`) compares the create's `skipped:false`/`notes:null` against the values a later op in the same batch set → `session_locked`. The client (`src/sync/flush.ts:112`) dead-letters both; `retryDeadLetterOp` (`src/sync/outbox.ts:102`) resends the same payload, which is rejected again forever.

**Reproduction (API, server B, any authenticated cookie):**
1. `POST /api/sync` with, in order: `workoutSession` upsert `{id:S, status:"in_progress", startedAt, blockId, templateId, templateName, weekIndex, isDeload:false, clientId:null, notes:null}`; three `sessionExercise` upserts (full rows, `skipped:false`); one more `sessionExercise` upsert for the curl slot with `skipped:true`; eight `setLog` upserts; `workoutSession` upsert `{id:S, status:"completed", completedAt, …}` → `applied: 12, rejected: []`.
2. `POST /api/sync` with the **identical body** → `applied: 10, rejected: [{session-create, "invalid_lifecycle_transition"}, {curl sessionExercise create, "session_locked"}]`; a third identical POST gives the same result. Row counts in `workout_sessions`, `session_exercises`, `set_logs`, `recommendations` are unchanged across all three POSTs (verified by `count(*)` before/after).

**Reproduction (real client, Playwright, production build):** log in → let the service worker take control → `context.setOffline(true)` → reload → *Start workout* → log two bench sets (101×5, 101×4) → *Complete workout* (outbox: 7 pending ops) → route `**/api/sync` so that the **first** request is forwarded with `route.fetch()` and its reply discarded with `route.abort()` → `context.setOffline(false)`. Observed: the lost reply was `{applied:[7 ids], rejected:[]}`; after the automatic retry the outbox is `pending:0, dead:["workoutSession:invalid_lifecycle_transition"]`; the banner reads **"1 change couldn't sync (invalid_lifecycle_transition)."**; `/api/history` holds the session with exactly `[101×5, 101×4]`; on `/sync-issues` "Retry" flips it to pending and it is dead-lettered again; only the double-confirmed Discard clears it.

**Impact:** no data loss and no divergence (the server state is exactly right), but the app tells the athlete a workout "couldn't sync" after the very scenario F6 is about, offers a Retry that cannot succeed, and requires a manual permanent discard. Reachable whenever a reply to a reconnect flush is lost after the server committed (page torn down by the offline shell's full navigation, iOS suspending the tab mid-request, a gateway reset) — the same class of loss the B-2 remediation accepted as real. **Classification: product defect** (same-environment controls: the identical batch applies cleanly the first time; the shipped single-op lost-response spec passes on the same stack; six *concurrent* identical batches converge with zero rejections).

**Remediation hint (not applied):** treat a create-shaped replay (`status:"in_progress"` with `startedAt` equal to the stored row's) against a terminal row as the no-op it is (evaluate the terminal-row tolerance before the lifecycle check, or compare against the row *as of the create*), and let a `sessionExercise` create replay tolerate differences only in fields a later op may set (`skipped`, `notes`) — or key replay idempotence on the op id.

### LOW-2 — Sub-16 px form controls on phone screens (iOS focus-zoom) — device-verifiable

Measured at 375×667 and 390×844: `/today` (recovery note input), `/today/workout` set-edit row (3 inputs, `src/ui/workout/ExerciseCard.tsx:286` and siblings inherit `text-sm`), add-ad-hoc search (`src/ui/workout/AddAdhocExercise.tsx`), `/exercises/new` and the exercise editor (`ContributionEditor` selects/weight, 6–9 controls), `/blocks/[id]` (`WeekOverrides`, 12 controls), `/recovery` (note), history set-edit rows (`src/ui/history/HistoryDetail.tsx:180`).

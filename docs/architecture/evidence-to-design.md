# Evidence-to-Design Map

Status: Accepted (2026-08-09)
Role: the traceability layer between the evidence corpus (`docs/evidence/`) and the architecture. Every science-adjacent design decision appears here with its evidence basis, its classification in the four-tier hierarchy, and — deliberately, per row — what the evidence does **not** justify. When a future change touches one of these decisions, this file is the first thing to update.

Sources: `docs/evidence/evidence-registry-reviewed.md` (EVIDENCE-001…031), `docs/evidence/product-evidence-boundaries.md` (principles A1–A12, heuristics B1–B11, preferences C1–C7), `docs/evidence/research-gaps.md` (GAP-01…10), `docs/input/rp-volume-landmarks.md` (coaching preset input, not evidence).

---

## 1. The four-tier hierarchy and where each tier lives in the system

These categories must never collapse into one another. Each has a distinct structural home:

| Tier | Meaning | Structural home |
|---|---|---|
| **Evidence-supported principle** | Directly backed by registry entries | Cited here and in doc rationale; shapes *what exists* (e.g., that multiple strategies exist at all). Never attached to a concrete numeric rule. |
| **Programming heuristic** | Plausible extrapolation (B1–B11), not itself tested | `classification: 'heuristic'` on shipped strategy configs; `source`/label metadata on seeded volume presets; caveat copy rules (volume-model §5). |
| **Configurable product rule** | A concrete setting the user can change | Prescription fields, strategy config JSON, deload config, landmark values, contribution weights — all editable data, none hard-coded. |
| **User-specific observation** | What this user actually logged | SetLogs, decisions, bodyweight, recovery entries — immutable facts. Never auto-promoted into rules; only read by strategies as inputs. |

Enforcement points: the `classification` enum on strategy configs has no reachable `'evidence_supported'` value for concrete triggers (ADR-006); seeded presets carry heuristic labels that the UI must render (volume-model §5); recommendation reason codes describe *behavior* ("all prescribed reps completed"), never scientific claims.

## 2. Decision-by-decision map

| # | Design decision | Evidence basis | Tier | What the evidence does NOT justify |
|---|---|---|---|---|
| 1 | Progression is a **registry of interchangeable strategies** (load-based, rep-based, manual; more later) rather than one built-in method. | EVIDENCE-031 (load vs. rep progression statistically indistinguishable, to failure, untrained); B9; GAP-03 ("support multiple strategies" is the supported claim). | Evidence-supported (the plurality), heuristic (everything more specific) | Any claim that one strategy is superior; generalization to trained lifters, multi-exercise programs, or non-failure training — EVIDENCE-031 is one 10-week single-exercise RCT. |
| 2 | Shipped default trigger rules (e.g., "all reps completed + final-set RIR in band → suggest +loadStepKg") are labeled `'heuristic'`, become `'user_defined'` when edited, and `'evidence_supported'` is unreachable for them. | B9 and GAP-03 draw exactly this line: progression plurality is evidence-supported; any specific numeric trigger is invention. | Programming heuristic → configurable rule | Marketing or UI copy describing any shipped trigger as "scientifically proven"; auto-tuning trigger thresholds "from the science" (no such science exists). |
| 3 | Default target-RIR band for hypertrophy work is **0–2**, expressed as a band, editable per prescription. | EVIDENCE-029 (1–2 RIR ≈ failure for hypertrophy, less fatigue); EVIDENCE-011/012/013 + conflict note (failure not required; curve shape disputed); B10. | Programming heuristic (defensible default, not optimum) | Treating 0–2 as a validated point-optimum; extending the same default to strength goals (proximity-to-failure is near-irrelevant for strength per EVIDENCE-011); resolving the Robinson-vs-Refalo curve-shape dispute in either direction. |
| 4 | RIR handled exclusively as **integer bands** with `met / below / above / unknown` checks; no fractional RIR, no averaging across sets, no correction algorithms; missing RIR degrades confidence instead of blocking. | EVIDENCE-030 (0.40–0.90 rep absolute error under best-case conditions); EVIDENCE-014; B11 (±1 rep tolerance is a data-handling posture, not a correction license). | Evidence-supported (noise exists) → heuristic (band mechanics) | Sub-repetition precision anywhere; silently "correcting" reported RIR by an offset; demographic trust-weighting of RIR (GAP-07: moderators contested). |
| 5 | Reports of RIR **above** the target band lower recommendation confidence rather than triggering aggressive jumps. | EVIDENCE-014 (self-estimated RIR less accurate far from failure); B8. | Programming heuristic | A quantitative accuracy model per RIR value; discarding high-RIR data entirely. |
| 6 | Secondary-muscle contribution defaults to **0.5** of a set, editable per exercise-muscle pair. | EVIDENCE-004 (fractional counting best-fitting model in one dose-response analysis); B2. | Programming heuristic (convention) | 0.5 as a biological constant; validated per-exercise or per-muscle weights; claiming derived per-muscle counts are measurements rather than a counting convention. |
| 7 | Volume landmarks are a **generic, swappable preset model** (free key vocabulary), with the RP MV/MEV/MAV/MRV table seeded as one labeled coaching preset; values editable; comparisons informational only. | GAP-01 (no per-muscle landmarks established; corpus's only landmark numbers are the RP coaching document); EVIDENCE-028 (muscle non-uniformity signal, coarse). | Configurable product rule wrapping a coaching heuristic | Presenting MEV/MAV/MRV as evidence categories; auto-computing or auto-adjusting a user's landmarks (GAP-01 explicitly blocks a default algorithm); treating volume above MRV as an error state. |
| 8 | Weekly set volume is the **primary tracked training quantity**, framed with diminishing returns, never with hard targets. | EVIDENCE-001/002/003 (positive, diminishing-returns pooled dose-response); A2. | Evidence-supported (direction), heuristic (any displayed reference range) | Exact optimal set counts; a universal ceiling; uniform response across muscles (EVIDENCE-028 found triceps ≠ quads/biceps at high volume). |
| 9 | Frequency is **not modeled as an independent training lever** — no frequency targets, no per-muscle frequency scoring; templates + weekday schedule simply distribute volume. | EVIDENCE-005/006 (hypertrophy near-null independent effect); B4. | 10 | Block **goal** (`strength` / `hypertrophy` / `general`) nudges defaults (rep ranges, load emphasis, RIR band) but never restricts user choice. | EVIDENCE-008/009/010 (load matters for strength; load zones interchangeable for hypertrophy near failure); EVIDENCE-024; B3; C1. | Evidence-supported (divergence), heuristic (each concrete default) | Forcing heavy loads for strength users (high-vs-moderate edge is only a trend); claiming any rep range is required for hypertrophy; goal-specific automation beyond defaults. |
| 11 | **Blocks/periodization are supported, never mandated**; no periodization-model picker; linear-style planned progressions available as strategy configs. | EVIDENCE-017/018/020/024 (modest strength-only benefit, volume-equated; linear edge trained-only); B5; C3. | Evidence-supported (optionality), heuristic (defaults) | Claiming periodization improves hypertrophy; pushing periodization models on beginners; "blocks are how training works" framing. |
| 12 | **Deloads are flexible**: scheduled per block config or manual via week override; modifiers (sets/load/RIR) user-set; deload weeks badged in volume, not excluded; post-deload dips framed as expected. | 13 | **No tempo or ROM prescription fields**; technique cues live in free-text exercise notes at most. | EVIDENCE-021 (2–8 s/rep equivalent); EVIDENCE-022 (long-length ROM a mild default only); C2; B7. | Evidence-supported (restraint) | A tempo/ROM prescription feature marketed as evidence-based; muscle-specific ROM rules (1–3 studies each). |

| 15 | Recommendations are **advisory records with an explicit user decision**; nothing auto-applies; the user always wins. | Follows from B9/GAP-03: with no validated triggers, auto-apply would launder heuristics into authority. | 16 | Exercise catalog carries **no per-exercise efficacy claims** — no "best for chest" rankings, no EMG-based ordering. | GAP-08 (exercise-selection efficacy outside corpus); EVIDENCE-026 (EMG not a validated hypertrophy predictor); C5/C6. | Evidence-supported (restraint) | Exercise-ranking features; "science-based exercise selection" copy; strict-technique claims (EVIDENCE-023: zero literature). |
| 17 | Onboarding/empty-state copy may say resistance training **works and is broadly safe** — nothing more specific. | EVIDENCE-016/019 (RT effective); GAP-10 (safety broad, not variable-specific); GAP-04 (long-term trajectories thin). | Evidence-supported (top-line only) | Variable-specific injury-risk claims ("high frequency is safe"); progress forecasts or predicted-gains charts (GAP-04). |
| 18 | e1RM (post-MVP analytics) is computed on read via a named formula and labeled an **estimate/convention**. | No corpus basis — the corpus never validates 1RM-estimation formulas. | Convention (heuristic, no corpus backing) | Presenting e1RM as measured strength; strategy triggers keyed to e1RM presented as evidence-based. |
| 19 | Muscle taxonomy v2 (ADR-010): `back` split into `lats` / `upper_back` leaves with `back` kept as a **derived analytical rollup**; seeded defaults **partition** each pulling exercise into exactly one leaf (vertical pulls → `lats`, rows → `upper_back`, hinge secondaries → `upper_back`); `adductors` added; leaf numbers framed as "sets directed at this bucket under the current convention". | EVIDENCE-028 (per-muscle response is non-uniform, so per-muscle *tracking* is useful — the only corpus signal); B2 / EVIDENCE-004 (fractional counting is a convention with tunable weights); GAP-01 (no per-muscle landmarks exist). ## 3. Standing rules derived from this map

1. **New science-adjacent features start here.** Before building, add the row: basis, tier, and the not-justified column. If the not-justified column would be empty, the claim is probably overreaching.
2. **The not-justified column is load-bearing.** Several MVP refusals (auto-deloads, auto-MEV/MRV, RIR correction, tempo fields) exist *because* of it; removing a refusal requires new evidence entering the registry, not a product whim.
3. **Preset/config edits never change tier.** A user tuning a heuristic default makes it `'user_defined'` — it does not become more (or less) scientific, and the UI must not imply otherwise.
4. **Corpus updates flow one way.** New papers → registry → boundaries/gaps revision → this map → design change. Design documents never cite papers directly; they cite EVIDENCE/GAP/B/C IDs so the interpretation layer stays single-sourced.
